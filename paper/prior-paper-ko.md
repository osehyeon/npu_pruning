## 1. 무엇을 한 연구인가

**모델을 고정한 채 시스템 스케줄링을 최적화함.** YOLOv3 와 Neubla Antara NPU 로
실시간 객체 검출 시스템을 구성하고 두 기법을 제안함.

```
더블 버퍼링    CPU 가 다음 프레임을 미리 처리해 NPU 유휴 시간을 없앰
큐 기반 처리   다중 NPU 에 작업을 분배하고 암달의 법칙으로 한계를 분석
```

CPU 단독 대비 처리량이 단일 버퍼링 2.13배, 더블 버퍼링 3.35배, 다중 NPU 4.81배임.
지연은 단일과 더블에서 1.6배, 다중 NPU 에서 1.18배 감소함.
정확도는 CPU 31.4 mAP, NPU 31.8 mAP 로 유지됨.

## 2. Antara NPU 사양

논문 Table 1 임.

| 항목 | Antara | Coral EdgeTPU | Hailo-8 |
|---|---|---|---|
| 성능 | 6 TOPS | 4 TOPS | 26 TOPS |
| 내장 SRAM | 1.5 MB | 8 MB | N/A |
| MAC 수 | 3 K · 1.5 K × 2 | N/A | N/A |
| 데이터 타입 | Int-8 | Int-8 | Int-8 |
| TOPS/W | 4 | 2 | 2.9 |

본문에는 `32 × 48 MAC array` 이고 `Int8/FP8` 을 지원한다고 적혀 있음.
`32 × 48 = 1,536` 이고 두 개면 3,072 로 표의 `3 K` 와 맞음.

### 우리 복원값과의 불일치

`docs/antara-npu-internals.png` 는 툴체인과 펌웨어에서 복원한 것인데 값이 다름.

| 항목 | 논문 | 우리 복원 |
|---|---|---|
| MAC array | 32 × 48 | TX array 64 × 32 |
| 유닛당 MAC | 1,536 | 2,048 |
| SRAM | 1.5 MB | 2 MB · `nbc -sram 2097152` |
| 데이터 타입 | Int8 · FP8 | EP 커널은 u8 · u16 · i16 만 노출 |

**출처가 다름.** 논문은 벤더가 제공한 값이고, 우리 것은 `nbc` 파라미터와 펌웨어
주소맵에서 역추적한 값임. 리비전 차이일 수도 있고 복원 오류일 수도 있음.

### 결정 · 2026-09-10

**FGCS 원고는 선행 논문의 값을 쓴다.** 32 × 48 MAC array · 6 TOPS · 1.5 MB SRAM.
공개된 출처가 그것뿐이고 인용할 수 있는 유일한 값임.

두 값이 모두 맞을 가능성이 있음. **저자 추측이며 확인되지 않았음.** 물리적 연산기 배열과
그 위에서 컴파일러가 제어하는 단위가 서로 다른 층위일 수 있고, 그렇다면 벤더가 밝힌
32 × 48 은 MAC array 이고 역추적된 64 × 32 는 TX 가 다루는 단위가 됨. 논문의 정렬 단위
64 가 후자와 맞아떨어지는 것도 이 해석과 어긋나지 않음.

**원고에는 이 해석을 쓰지 않음.** 근거가 없으므로 사양은 선행 논문 값만 인용하고,
정렬 단위 64 는 사양이 아니라 타일 수 1,455 사례 일치로 뒷받침함.

## 3. 작업 분할

### 단계 구성

```
데이터 획득 → 전처리 → 추론 → 후처리 → 결과 출력
```

데이터 획득 · 전처리 · 후처리 · 결과 출력은 CPU 가 맡고 추론만 NPU 가 맡음.

### Backbone · Neck · Head

```
Backbone   특징 추출 · 병렬 연산 많음      NPU
Neck       다중 스케일 융합               NPU
Head       박스 회귀와 클래스 예측 · 가벼움  CPU
```

**우리 조사와 일치함.** EP 커널 등록표에 `Sigmoid` · `TopK` · `NonMaxSuppression`
이 없어 Head 는 구조적으로 CPU 에 남음. 논문은 이를 효율 선택으로 서술했으나
실제로는 제약임.

## 4. 양자화와 컴파일

비대칭 양자화에 이동평균 보정을 적용해 8비트로 변환함.
우리가 `requantize.py` 에서 재현한 `CalibMovingAverage` 조건과 같음.

### 컴파일 옵션별 실행 시간

논문 Table 2 임. **후속 연구에서 가장 중요한 표임.**

| 구성 | LW · Single | LW · Half | EGS · Single | EGS · Half |
|---|---|---|---|---|
| 실행 시간 ms | 56.80 ± 0.48 | 48.13 ± 0.51 | 32.87 ± 0.47 | 26.06 ± 0.50 |

옵션 설명은 이럼.

```
LW    Layer-wise · 계층마다 따로 그룹을 만듦
EGS   Exhaustive Group Search · 의존성과 메모리를 보며 최대한 묶음
Single  TX 엔진 하나가 64채널 단위로 OFM 계산
Half    TX 엔진 둘이 각각 64채널 단위로 나눠 계산
```

### 시사점

**컴파일 옵션만으로 2.18배가 남.** `56.80 → 26.06` 임.

우리가 프루닝으로 얻은 가속은 `58.4 → 40.8` 로 1.43배임.
**컴파일 옵션 선택이 프루닝보다 효과가 큼.**

우리 원본 `lw · single` 측정 58.4 ms 는 논문의 56.80 ms 와 근접해 측정 정합성이 확인됨.

`Half` 는 아직 한 번도 안 써봄. 프루닝 12종에 대해 `EGS · Half` 까지 재면
네 조합 × 13 모델의 격자가 완성됨.

## 5. 더블 버퍼링과 큐 기반 처리

### 파이프라인 구성

```
입력 파이프라인   데이터 획득 + 전처리            CPU
신경망 처리       Backbone + Neck                NPU
출력 파이프라인   Head + 후처리 + 결과 출력       CPU
```

**단일 버퍼링**은 셋을 순차 실행함. CPU 가 다음 입력을 준비하지 않으므로
NPU 가 노는 구간이 생김.

**더블 버퍼링**은 버퍼 두 개를 번갈아 써서 CPU 와 NPU 가 동시에 돎.
처리량이 오르는 대신 메모리 사용이 두 배가 됨. 임베디드에서는 부담이 될 수 있음.

### 큐 기반 처리

다중 NPU 에서 카메라 소유권 문제가 생김. 카메라는 한 주체에만 소유권을 주므로
여러 NPU 가 동시에 접근할 수 없음.

CPU 가 카메라에서 받아 입력 큐에 넣고, 각 태스크가 큐에서 꺼내 전처리 · 추론 · 후처리를
수행한 뒤 출력 큐에 넣음. NPU 수를 늘리면 처리량이 오르나 CPU · 메모리 대역폭 ·
I/O 제약으로 선형이 아님.

### 하드웨어 구성별 성능

논문 Table 5 임. `*` 는 더블 버퍼링, `†` 는 FP32, 나머지는 UINT8 임.

| 구성 | 처리량 FPS | 지연 ms | 정확도 mAP |
|---|---|---|---|
| Intel i7-12700 CPU · 기준 | 11.14 | 99.73 | 31.4 |
| Antara NPU | 24.41 | 38.34 | 31.8 |
| Antara NPU * | 38.38 | 37.77 | 31.8 |
| Antara NPU × 2 * | 55.04 | 81.88 | 31.8 |
| Intel i7-12700 CPU † | 5.37 | 187.43 | 31.4 |
| Jetson AGX Orin GPU † | 5.68 | 261.61 | 31.4 |
| GTX 1060 6 GB GPU † | 14.02 | 79.48 | 31.4 |

### 암달의 법칙 분석

다중 NPU 에서 처리량이 55.04 FPS 로 올랐으나 선형이 아님.
CPU 의 전처리와 후처리가 병목이 됨.

```
S = 1 / ((1 − P) + P/N)
P = 0.63 · N = 2  →  S = 1.46
예측 56.03 FPS · 실측 55.04 FPS
```

**예측 오차 1.8 % 로 모델이 검증됨.** 단일 NPU 실측만으로 다중 NPU 를 투영하는 것이
정당화되는 근거임.

## 8. 후속 연구와의 연결

### 축이 직교함

```
선행   모델 고정 · 시스템 스케줄링 최적화
후속   시스템 고정 · 모델 압축과 컴파일 최적화
```

### 이어지는 주장

프루닝은 **NPU 단계만** 줄임. CPU 단계 15.20 ms 는 그대로임.
더블 버퍼링에서 처리량은 가장 긴 단계가 정하므로, NPU 가 15.20 ms 아래로 내려가면
그 이후의 프루닝은 처리량에 아무 효과가 없음.

```
필요한 가속    25.76 / 15.20 = 1.70배
우리가 얻은 것 1.43배
```

포화 직전까지 갔고 아직 닿지는 않았음. 이 간극이 후속 논문의 핵심 수치가 됨.

### 같은 현상이 두 층위에 있음

```
시스템 층위   CPU 단계 15.20 ms 가 바닥
NPU 내부      메모리 이동이 전체 시간의 65 % 이고 압축에 반응하지 않음
```

MACs 를 46 % 줄여도 `MEM_LDA` 는 11 % 만 줄어듦. 컴파일러 스케줄 트레이스에서
확인한 값임.

### 반드시 반영해야 할 것

**컴파일 옵션이 프루닝보다 효과가 큼.** 논문 Table 2 가 `LW · Single 56.80` 에서
`EGS · Half 26.06` 으로 2.18배를 보임. 프루닝만 다루면 더 큰 요인을 놓치는 셈임.

후속 논문은 **압축과 컴파일 옵션을 함께 놓는 격자**로 가는 것이 맞음.

```
압축      원본 + ratio 3종 × staircase 4종
컴파일    LW/EGS × Single/Half
```

`EGS · Half` 는 아직 한 번도 측정하지 않았음.
