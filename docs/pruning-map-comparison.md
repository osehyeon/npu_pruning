# 프루닝 정확도 손실 측정 (COCO mAP)

> 작성일: 2026-08-02 · 스크립트: [../example/eval_map.py](../example/eval_map.py), [../example/decoders.py](../example/decoders.py)
> 모델: [../model/README.md](../model/README.md)

원본 YOLOv3 와 Nota AI 의 40 % / 50 % 프루닝 모델을 **같은 이미지 집합**으로 비교했습니다.

> ## 🛑 먼저 읽으세요 — [model-lineage-warning.md](./model-lineage-warning.md)
>
> 워크스페이스에 **서로 다른 세 가지 YOLOv3** 가 `yolov3` 라는 이름으로 섞여 있습니다.
> 특히 **배포된 원본 uint8(mmdet 계열)과 `yolov3_original_fp32.onnx`(Nota 학습 계열)는
> 다른 모델**입니다(첫 Conv 상관 −0.05).
>
> 이 문서의 아래 표들 중 **두 계보를 가로지르는 비교는 무효**입니다.
> 유효한 것은 `yolov3_original_fp32` ↔ `pruned40/50_fp32` (같은 계보, 상관 1.0000) 뿐입니다.

## 방법

| 항목 | 값 |
|---|---|
| 데이터 | COCO **val2017 전체 5,000장** (일부 보조 실험은 500장 부분표본) |
| 지표 | `pycocotools` COCOeval bbox — AP(0.5:0.95) / AP50 / AP75 / APs·m·l |
| 입력 | 608×608 단순 resize (letterbox 아님) · RGB · `/255` |
| 정밀도 | **float32, CPU** — NPU 미사용. 순수 프루닝 손실만 분리 |
| 최대 검출 | 100 / 이미지 · score ≥ 0.001 · NMS IoU 0.45 |

표본 크기에 따라 절대값이 크게 흔들립니다. 최종 수치는 **전체 5,000장**을 씁니다.

| 표본 | 원본 AP |
|---|---:|
| 150장 | 42.07 |
| 500장 | 40.72 |
| **5,000장 (전체)** | **38.26** |

> ⚠️ **절대값이 논문 수치보다 4.6점 높습니다 — 원인 미규명.**
> 참고 기준: mmdet `yolov3_d53_mstrain-608_273e_coco` **33.7** (val2017 전체) ·
> Redmon 2018 YOLOv3-608 **33.0** (test-dev).
> 전체 5,000장으로 재도 38.26 이라 표본 편향이 아닙니다.
> **평가 프로토콜 차이**(우리는 단순 resize + `/255`, mmdet 은 letterbox + 정규화)가
> 유력한 후보이나 확인하지 못했습니다. 모델 간 비교에는 영향이 없습니다.

> 디코더가 모델마다 다릅니다 — 아래 "함정" 절 참조. 각 모델에 맞는 디코더를 썼습니다.

## 어느 표를 봐야 하는가

**계보가 같은 비교만 유효합니다.**

### ✓ 유효 — Nota 학습 계열 안에서 (프루닝의 진짜 손실)

| 조건 | 원본 | 40 % | 격차 |
|---|---:|---:|---:|
| fp32 (5,000장) | 38.26 | 30.19 | **−8.08** |
| fp32 (500장) | 40.72 | 33.75 | −6.97 |
| uint8 MovingAverage·배포calib (500장) | 38.34 | 32.35 | **−5.99** |
| uint8 MovingAverage·COCO calib (500장) | 38.62 | 32.03 | −6.59 |
| uint8 MinMax (500장) | 35.73 | 30.94 | −4.79 |

**프루닝 40 % 의 실제 손실은 약 6~8점입니다.**
양자화가 이 격차를 크게 줄여주지 않습니다.

### ✗ 무효 — 계보를 가로지르는 비교

```
배포 원본 u8 28.92  vs  40 % u8 28.59   →  격차 −0.33 "거의 무손실"
                                            ← mmdet 계열 vs Nota 학습 계열. 무의미
NPU 실측    29.13  vs        28.66      →  격차 −0.47   ← 동일한 문제
```

이 두 줄이 *"프루닝이 배포에서 거의 공짜"* 라는 결론의 근거였는데,
**배포 원본이 다른(그리고 더 낮은 점수의) 모델**이라 성립하지 않습니다.

### 정정 이력 — 세 번 틀렸습니다

| | 주장 | 왜 틀렸나 |
|---|---|---|
| 1차 | uint8 손실 −0.13, "거의 공짜" | 배포 모델들이 서로 다른 설정으로 양자화됨 |
| 2차 | MinMax 통제 시 −4.79, "효과는 2.18점 축소" | 배포는 MovingAverage 였음 |
| 3차 | MovingAverage 통제 시 −6.59, "효과 없음" | 방향은 맞았으나 배포 원본과의 6점 격차 미해명 |
| **최종** | **약 −6~8점. 양자화는 격차를 줄이지 않음** | **배포 원본이 다른 계보임을 확인** |

## ✅ 평가 파이프라인 검증 — ultralytics 와 0.12 이내로 일치합니다

`yolo_val/` 은 Neubla 가 **ultralytics `val.py`** 로 돌린 검증 환경이고,
`runs/val/exp14/` 에 5,000장 예측 JSON 이 남아 있습니다.
그 모델 `yolov3-mod-precomile-quantize.onnx` 는 제 fp32 원본과
**첫 Conv 상관 +0.9999** — 같은 모델의 uint8 양자화본입니다.

**같은 모델을 양쪽 파이프라인으로 재서** 변수를 하나씩 분리했습니다 (전부 5,000장):

| # | 모델 | 양자화 | 전처리 | 구현 | AP |
|---|---|---|---|---|---:|
| ① | 원본 fp32 | 없음 | resize | 제 것 | 38.26 |
| ② | 원본 u8 | Neubla | resize | 제 것 | 36.21 |
| ③ | 원본 u8 | 내 재양자화 | resize | 제 것 | 35.87 |
| ④ | 원본 u8 | Neubla | **letterbox** | 제 것 | **38.26** |
| ⑤ | 원본 u8 | Neubla | **letterbox** | **ultralytics** | **38.14** |

```
④ − ⑤ = 0.12   ← 두 독립 구현이 일치.  평가 파이프라인 검증 완료
④ − ② = 2.05   ← 전처리만의 효과. letterbox 가 종횡비를 보존해 유리
② − ③ = 0.34   ← 양자화 방법 차이. 제 재양자화 ≈ Neubla 양자화
```

**같은 모델·같은 가중치·같은 전처리로 맞추면 제 파이프라인과 ultralytics `val.py` 가
0.12 AP 이내로 일치합니다.** 절대값 신뢰성 문제는 해소되었습니다.

### ⚠️ 정정 이력 — 검증 논리를 두 번 고쳤습니다

| | 주장 | 왜 틀렸나 |
|---|---|---|
| 1차 | *"38.14 vs 38.26, 0.12 차이 → 검증됨"* | ⑤(uint8)와 ①(fp32)을 비교. 두 오차(letterbox +2.05, 양자화 −2.05)가 우연히 상쇄된 것 |
| 2차 | *"제 양자화가 2.4 열등"* | 실제로는 0.34. 나머지는 전처리 차이였음 |
| **최종** | **④ vs ⑤ 로 조건을 맞춰 0.12 확인** | — |

### 전처리 선택이 절대값에 미치는 영향

`cv2.resize` 는 종횡비를 왜곡해 표준(letterbox) 대비 **약 2.0 AP 낮게** 나옵니다.
`--letterbox` 옵션으로 표준 방식 측정이 가능합니다:

```bash
python eval_u8_final.py neubla_q --limit 0 --letterbox
```

**상대 비교(프루닝 손실)는 모든 모델이 같은 전처리를 타므로 영향받지 않습니다.**

### 33.7 과는 여전히 무관합니다

33.7 은 **mmdet 계열**(배포 원본, 첫 Conv 상관 −0.05)의 공표값입니다.
우리 프루닝 실험 모델들과는 다른 모델이므로 애초에 대조 대상이 아닙니다.
자세한 대조: [model-lineage-warning.md](./model-lineage-warning.md)

## 읽는 법 (fp32 기준)

### fp32 만 보면 손실이 큽니다

40 % 프루닝에 AP 8.08점(상대 21 %)은 일반적인 구조적 채널 프루닝 기대치보다 큰 편입니다.
동일조건 uint8(MovingAverage)에서도 격차는 **6.59** 로 거의 그대로 유지됩니다 —
**양자화가 이 격차를 줄여주지 않습니다.**

### 작은 객체가 먼저 무너집니다

```
APs   27.31 → 18.38 → 14.68     (−33 % / −46 %)
APm   41.80 → 32.49 → 27.17     (−22 % / −35 %)
APl   48.40 → 37.28 → 32.41     (−23 % / −33 %)
```

**작은 객체 손실이 큰 객체의 두 배**입니다. 채널을 줄이면 고해상도 헤드(76×76)의
표현력이 먼저 희생된다는 뜻입니다. 작은 객체가 중요한 용도라면 프루닝을 신중히 봐야 합니다.

### 50 % 는 수지가 안 맞습니다

40 % → 50 % 로 갈 때:

- AP 는 **4.1점 더** 떨어지고 (30.19 → 26.13)
- NPU 속도는 **4 %만** 늘어납니다 (1.18× → 1.23×)

**40 % 가 균형점**으로 보입니다.

### 속도 이득이 채널 감소분에 못 미칩니다

채널이 37 % 줄었는데 CPU 속도는 1.78× (= 44 % 단축)입니다.
**NPU 에서는 더 작습니다 — 1.18×** ([아래](#npu-실측-속도) 참조).

프루닝이 **512·1024 채널의 후반부 레이어**에 집중됐는데, 그쪽은 해상도가 낮아(19², 38²)
파라미터는 많아도 **실제 MAC 연산량 비중이 작습니다.** 반대로 앞쪽 76² 레이어는
채널이 적어 손대지 않았습니다. 그래서 파라미터 37 % 감소가 연산량 37 % 감소로 이어지지 않습니다.

## 동일 조건 재양자화 — 교란변수 제거

세 fp32 모델을 **같은 캘리브레이션 이미지**로 다시 양자화해, 캘리브레이션 **방식**과
**장수**를 함께 훑었습니다 (`example/requantize.py`, `eval_calib_sweep.py`).

공통 설정: `QuantFormat.QOperator` · `per_channel=False` · uint8 · 평가 500장

### `MovingAverage` 의 정체

Neubla devkit 소스(`quantization/ort_quant_manager.py:135`)를 보면 별도 방식이 아닙니다:

```python
calibration_method = CalibrationMethod.MinMax
extra_options["CalibMovingAverage"] = True
extra_options["CalibMovingAverageConstant"] = 0.01
```

**MinMax + 지수이동평균(계수 0.01)** 입니다. min/max 를 이미지마다 EMA 로 갱신하므로
**이상치 하나가 범위를 넓히지 못합니다.** 표준 ORT 1.12.1 이 이 옵션을 지원해
배포 조건을 그대로 재현할 수 있었습니다.

### 결과 — 방식이 결정적입니다

**AP (평가 500장)**

| 모델 | fp32 (500) | MinMax c100 | **MovingAverage c100** |
|---|---:|---:|---:|
| 원본 | 40.72 | 35.73 | **38.62** |
| 40 % 프루닝 | 33.75 | 30.94 | **32.03** |
| 50 % 프루닝 | 27.93 | 25.68 | **26.36** |

**양자화 손실 (같은 500장 기준)**

| 모델 | MinMax | **MovingAverage** |
|---|---:|---:|
| 원본 | **−4.99** | **−2.10** |
| 40 % 프루닝 | −2.81 | **−1.72** |
| 50 % 프루닝 | −2.25 | −1.57 |

**`CalibMovingAverage=True` 한 줄로 원본이 2.9점을 회복합니다.**
이상치가 스케일을 흔드는 것을 막는 효과가 그만큼 큽니다.

### 캘리브레이션 장수 경향이 뒤집힙니다

```
MinMax         원본  −1.70 → −4.04 → −4.99      (1 → 20 → 100장)   많을수록 나빠짐
MovingAverage  원본  −0.76 → −0.50 → −0.36                        많을수록 좋아짐
```

순수 MinMax 는 이미지가 늘수록 극단값을 더 잡아 스케일이 거칠어집니다.
EMA 를 걸면 통계가 안정되어 **정상적인 방향**으로 돌아옵니다.

### 프루닝 격차 — "양자화 견고성" 은 방식 아티팩트였습니다

```
fp32                 40.72 vs 33.75    격차 6.97
MinMax    c100       35.73 vs 30.94    격차 4.79   ← 좁아진 것처럼 보임
MovingAvg c100       38.62 vs 32.03    격차 6.59   ← fp32 와 거의 같음
```

**배포 조건(MovingAverage)으로 통제하니 격차가 fp32 와 거의 같아집니다.**
MinMax 에서 관측된 축소(6.97 → 4.79)는 **캘리브레이션 방식이 만든 착시**였습니다.

> 앞서 세웠던 *"압축이 양자화 견고성을 부수적으로 개선한다"* 는 가설은
> **이 통제 실험에서 지지되지 않습니다.**

### 원인 가설 검증 기록

| 가설 | 검증 방법 | 결과 |
|---|---|---|
| `exp` 디코더가 양자화 오차를 지수 증폭 | wh 오차 전파 분석 | ❌ 상대오차 차이 1.2~1.3배뿐. `exp(t+δ)/exp(t)=e^δ` 라 **상대오차를 보존**함 |
| 원본만 후처리까지 양자화됨 | 후처리 분리 재평가 | ❌ 차이 0.00. 해당 모델의 후처리부는 원래 float |
| 프루닝 재학습이 가중치를 양자화 친화적으로 만듦 | 가중치 분포 + 동일조건 재양자화 | ❌ MovingAverage 통제 시 격차가 fp32 와 동일. **MinMax 아티팩트** |

**세 가설 모두 기각되었습니다.**

## ✅ 해결됨 — 6점 격차의 정체는 다른 모델이었습니다

한동안 다음 두 값이 6점 넘게 어긋나 원인을 찾지 못했습니다:

## 함정 — 모델마다 디코더가 다릅니다

**처음 측정에서 프루닝 AP 가 12.70 / 10.91 로 나왔습니다. 측정 오류였습니다.**

두 모델은 **박스 크기(wh) 디코딩 공식이 다릅니다.**

```
표준 YOLOv3 (원본)     wh = exp(t) · anchor
Nota 프루닝            wh = 2·(tanh(t/2 − 0.549306) + 1) · anchor
```

수식을 정리하면 정체가 드러납니다 — `0.549306 × 2 = 1.098612 = ln 3` 이므로

```
2·(tanh(t/2 − 0.549306) + 1)  ≡  4·σ(t − ln 3)        (수치 오차 3e-7)
```

즉 **`4 × 시그모이드`**, YOLOv5 가 `exp` 대신 도입한 bounded wh 디코딩과 같은 계열입니다.
`ln 3` 평행이동은 `t=0` 에서 정확히 `1.0` 이 되도록(=`exp(0)` 과 일치) 맞춘 것입니다.

| t | `exp(t)` | tanh 식 |
|---:|---:|---:|
| 0 | 1.00 | 1.00 |
| 3 | 20.09 | 3.48 |
| 10 | **22,026** | 3.9995 |
| ∞ | **∞** | **4.0** |

### 왜 바꿨나 — 실측이 설명합니다

COCO 20장에서 **wh 채널 출력값 분포**를 직접 쟀습니다:

| 모델 | wh min | wh max | `exp` 적용 시 | tanh 식 적용 시 |
|---|---:|---:|---:|---:|
| original | −3.22 | 2.39 | 10.9 × anchor | 3.14 × anchor |
| **pruned40** | −2.50 | **20.68** | **953,074,240 × anchor** | **4.00 × anchor** |

**프루닝 모델의 wh 는 최대 20.68 까지 튑니다.** `exp` 를 씌우면 앵커의 **9억 배** 박스가 나옵니다.
잘못된 디코더로 AP 가 12점까지 무너진 이유가 이것입니다.

이유는 둘로 보입니다:

1. **프루닝이 출력을 불안정하게 만듭니다.** 채널을 37 % 걷어내면 남은 채널이 더 큰 값을
   내야 같은 표현력을 유지합니다 (wh max 2.39 → 20.68, 8.6배). `exp` 를 그대로 뒀다면
   학습이 발산했을 것입니다.
2. **NPU uint8 per-tensor 양자화에 `exp` 는 치명적입니다.** 텐서 하나에 스케일 하나뿐인데
   `exp` 이전 값이 −3~20 이면 스텝 오차가 큰 `t` 에서 박스 크기로 수백~수천 픽셀 증폭됩니다.
   `4σ` 는 어떤 입력이 와도 출력이 [0, 4] 에 갇힙니다.

> 2번은 정황이 강하지만 **Nota 의 설계 문서를 확인한 것은 아닙니다.**
> 확실한 것은 수식이 `4σ(t−ln3)` 라는 것, wh 가 실제로 20을 넘는다는 것,
> 그래서 `exp` 로는 못 쓴다는 것까지입니다.

### 디코더별 실측 (20장)

| 모델 | `exp` 디코더 | `tanh` 디코더 |
|---|---:|---:|
| original | **AP 37.41** | 34.44 |
| pruned40 | 12.70 | **AP 33.97** |
| pruned50 | 10.91 | **AP 30.08** |

각 모델이 자기 디코더에서 최고를 냅니다. 원본에 tanh 를 쓰면 3점 손해,
프루닝에 exp 를 쓰면 **21점** 손해입니다.

```
              50 %  −10.72     속도 1.21×   (90.5 → 74.8 ms)
```

40 % → 50 % 는 속도를 **2.1 %** 더 얻자고 AP 를 **3.88점** 더 내주는 거래입니다.
`egs` 표에서 관측한 것과 같은 결론이며, **40 % 가 균형점**입니다.

### CPU 예측과의 대조

| 기준 | 원본 | 40 % | 격차 |
|---|---:|---:|---:|
| CPU uint8 resize | 35.87 | 28.55 | −7.32 |
| **NPU R 계열** | **35.47** | **28.63** | **−6.84** |

격차가 0.5 이내로 맞습니다. **CPU uint8 시뮬레이션이 NPU 를 잘 예측한다**는 결론이
계보를 통제한 조건에서도 유지됩니다.

### 측정 중 고친 것 두 가지

1. **`.back` 의존** — `eval_map_npu.py` 가 디코더 종류(`exp`)만 보고 후처리 ONNX 를
   찾았습니다. `.back` 은 Neubla 배포본에만 딸려 있고 재양자화본(`R_*`)은 헤드가 그대로
   그래프 출력이라 필요 없습니다. **파일 존재 여부로 판단**하도록 바꾸고,
   numpy 표준 디코더 `decoders.decode_std`(`wh = exp(t)·anchor`)를 추가했습니다.
   검증: `.back` 이 있는 `N_orig` 을 두 경로로 200장 측정 → **39.27 vs 39.10 (0.17)**.
   `NPU_NUMPY_DECODE=1` 로 numpy 경로를 강제할 수 있습니다.
2. **0 바이트 캐시** — `build_front` 가 `/tmp/*.front.onnx` 를 존재 여부로만 판단해서,
   디스크가 찼을 때 생긴 0 바이트 파일 때문에 `R_50` 이 계속 실패했습니다.
   크기까지 확인하도록 고쳤습니다.

```bash
cd ~/workspace_docs/example
LIMIT=0 ./run_map_npu.sh R_orig R_40 R_50      # 모델당 약 8분
```
