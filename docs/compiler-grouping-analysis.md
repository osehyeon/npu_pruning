# 컴파일러 그룹 탐색이 지연을 지배한다 — lw 대 egs

> 작성일 2026-08-24 · 근거 `example/nbc_artifacts/{lw,egs}/*/  ` 의 nbc 스케줄 트레이스
> 관련 [nbc-compile-options.md](./nbc-compile-options.md) · [antara-clock-control.md](./antara-clock-control.md)

## 요약

**`egs` 의 이득은 거의 전부 메모리 이동 감소에서 나옵니다. 연산 시간은 그대로입니다.**

```
MEM 계열   평균 3.64배 감소
TX 계열    평균 0.99배 · 변화 없음
전체       평균 1.91배 감소
```

선행 논문이 실측한 `LW 56.80 → EGS 32.87 ms` 즉 1.73배와 방향과 크기가 맞습니다.

---

## 1. 데이터 출처

`nbc` 는 컴파일할 때 그룹마다 Chrome trace 형식의 스케줄 파일을 남깁니다.

```
NeublaExecutionProvider_NEUBLA_0_0_variant.onnx_group_N.json
```

`tid` 가 실행 유닛 이름이고 `dur` 이 그 유닛의 예상 소요 시간입니다.
유닛 이름은 시뮬레이터 헤더의 `UnitType` 과 일치합니다.

```c
enum class UnitType { TX, VX, CCU, Reshaper, DDMA_LOAD, DDMA_STORE, Broadcaster, SCU };
tx_units 2 · vx_units 2 · reshaper_units 1 · ddma_load_units 1 · ddma_store_units 1
```

작업 디렉터리를 덮어쓰므로 모델마다 따로 보관해야 합니다.
`example/compile_sweep_keep.sh` 와 `example/compile_egs_rest.sh` 가 그 일을 합니다.

## 3. 감소 배수

| model | group | MEM_LDA | MEM_STA | MEM 합 | TX 합 | 전체 |
|---|---|---:|---:|---:|---:|---:|
| sw10sc8 | 85→21 | 5.76x | 4.50x | 2.85x | 1.00x | 1.71x |
| sw10sc64 | 82→20 | 5.85x | 4.41x | 2.84x | 1.00x | 1.70x |
| sw30sc8 | 88→20 | 5.53x | 4.55x | 3.27x | 1.00x | 1.84x |
| sw30sc64 | 82→14 | 7.00x | 5.19x | 3.67x | 1.00x | 1.90x |
| sw50sc8 | 88→12 | 7.82x | 5.89x | 4.63x | 1.00x | 2.20x |
| sw50sc64 | 82→9 | 7.93x | 5.85x | 4.68x | 1.00x | 2.16x |
| **평균** | | | | **3.64x** | **0.99x** | **1.91x** |

### 읽는 법

**`TX 합` 이 1.00배입니다.** 연산량은 컴파일 옵션과 무관하므로 당연한 결과이고,
트레이스가 신뢰할 만하다는 검증이기도 합니다.

**`MEM` 이 3.64배 줄어듭니다.** `egs` 가 그룹을 크게 묶으면 중간 결과가 SRAM 에
머물고 DRAM 왕복이 사라집니다. 그룹 수가 82~88 에서 9~21 로 줄어드는 것과
정확히 대응합니다.

**압축률이 높을수록 이득이 큽니다.** 10 % 에서 1.71배, 50 % 에서 2.20배입니다.
모델이 작아져 더 많은 연산이 2 MB SRAM 안에 들어가기 때문으로 보입니다.

## 4. 병목이 뒤집힙니다

`sw50sc64` 기준입니다.

| 옵션 | MEM | TX | 기타 |
|---|---:|---:|---:|
| lw | 68.3 % | 31.6 % | 0.1 % |
| egs | 31.5 % | 68.3 % | 0.3 % |

**`lw` 는 메모리 병목, `egs` 는 연산 병목입니다.** 정확히 뒤집힙니다.

이는 프루닝의 효과에도 영향을 줍니다.

```
lw   에서 프루닝은 MEM 을 못 줄이므로 이득이 제한됨
egs  에서 프루닝은 TX 를 직접 줄이므로 이득이 더 크게 남을 수 있음
```

`egs` 바이너리를 보드에서 측정하면 이 예측을 검증할 수 있습니다.

## 5. 선행 논문과의 정합

선행 논문 Table 2 는 원본 모델의 실측값입니다.

| 구성 | LW · Single | LW · Half | EGS · Single | EGS · Half |
|---|---|---|---|---|
| 실행 시간 ms | 56.80 | 48.13 | 32.87 | 26.06 |

```
실측 LW → EGS      56.80 / 32.87 = 1.73배
우리 추정 평균                      1.91배
```

우리 추정이 조금 큰 것은 대상이 프루닝 모델이고 압축률이 높을수록 이득이 커지기
때문입니다. 10 % 구간만 보면 1.70~1.71배로 실측 1.73배와 거의 일치합니다.

**컴파일러 트레이스가 실측을 예측할 수 있음을 보여줍니다.**

## 6. 논문에 쓸 주장

### 압축보다 컴파일 옵션이 큽니다

```
프루닝 50 %      NPU 58.4 → 40.8 ms    1.43배
컴파일 lw → egs  56.80 → 32.87 ms      1.73배
tx_ofm_step half 추가                   1.26배
합쳐서                                  2.18배
```

**모델을 절반으로 줄이는 것보다 컴파일 옵션을 바꾸는 것이 효과가 큽니다.**
압축 논문이 컴파일 설정을 고정한 채 보고하면 더 큰 요인을 놓치는 셈입니다.

### 두 기법이 겨냥하는 곳이 다릅니다

```
프루닝       연산량을 줄임        MEM 은 거의 그대로
그룹 탐색    메모리 이동을 줄임   TX 는 그대로
```

**직교합니다.** 따라서 함께 적용하면 곱해질 가능성이 있고, 이것이 이번 연구가
격자로 실험해야 하는 이유입니다.

### 남은 검증

`egs` 바이너리 12종을 보드에서 실측해야 합니다. 현재는 컴파일러 추정치뿐입니다.
보드가 DMA 고장이라 재부팅이 선행되어야 합니다.

`tx_ofm_step half` 는 아직 한 번도 컴파일하지 않았습니다.
네 조합 격자를 완성하려면 24회 컴파일이 더 필요합니다.

## 7. 주의

`egs` 는 벤더 검증 스크립트가 두 단계에서 중단됩니다.

```
1차   util.py 의 skip_nodes 가 원본 모델 이름으로 하드코딩됨
2차   verify.py:99 te.inst() 의 pybind 바인딩 결함
```

둘 다 검증 단계 문제이고 컴파일과 시뮬레이션은 정상 완료됩니다.
`example/compile_variant_skipconcat.sh` 가 1차를 우회하고,
`example/compile_egs_rest.sh` 가 예외 후 `.o` 를 회수합니다.

**수치 검증을 건너뛴 바이너리이므로 보드 실측 시 mAP 를 함께 확인해야 합니다.**
